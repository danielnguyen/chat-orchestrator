# CCP subtractive architecture audit — Chat Orchestrator

Assessment date: 2026-11-15. Scope: [CO issue #240](https://github.com/danielnguyen/chat-orchestrator/issues/240). This report proposes removals for independent review. It changes no executable behavior and grants no implementation, merge, deployment, migration or hold waiver.

## Executive recommendation

Preserve the useful private Telegram conversation and its durable continuity while reducing the number of competing ways to produce an answer. Keep CO as the canonical request coordinator, Basic Memory Store (BMS) as durable memory/publication authority, and Cognitive Runtime (CR) as runtime admission and policy authority. The strongest confirmed whole-system duplication is BMS's second chat pipeline. Retiring it after caller verification is more substantial than splitting CO's large functions into modules.

Within CO, start with four apparently unreachable helpers and duplicated timing-contract definitions. Then investigate retiring redundant evidence presentation paths and delegating provider reliability mechanics to the already-used LiteLLM gateway. Those larger changes are conditional: source proves overlapping machinery, not safe equivalence or production non-use. Preserve recipient-side validation, local-only routing, exact evidence association, prompt-retention checks and restart/publication fencing. A generic agent framework or shared policy service would add ownership and migration costs without demonstrated need.

The priority for user value is avoiding unnecessary external-evidence work on questions answerable from supplied context. Existing fixes and calibration modes already address parts of this problem; neither proves the remaining natural-language routing defect solved. Do not reopen paused #225/#237 or #217 through this audit. No percentage reduction, latency saving or maintenance-hour estimate is supported by this investigation.

## Source-traced request and data flow

```text
Private Telegram adapter: truthful owner/client/surface and optional conversation_id
  -> CO /v1/chat: API-key dependency, validated ChatRequest, request identity
  -> BMS permission + durable conversation/lifecycle; CR selection/admission
  -> CR policy; BMS profile/current user persistence/scoped memory retrieval
  -> optional history explanation OR governed DSA evidence acquisition
  -> CO filtered, layered, budgeted prompt -> LiteLLM -> bounded fallback/output gates
  -> BMS assistant + trace + optional associated claims; CR exact turn completion
  <- synchronous response OR existing durable-work result; adapter delivers
```

Early clarification, denial, explicit pause and provider-free responses bypass later stages. The diagram does not imply every optional policy runs, nor one transaction spanning services.

### Feature and dependency distinctions

[Settings][C-settings] default runtime overlays, companion/governance/containment/restraint/privacy/hygiene/capability policies, strict modes, claim capture, evidence acquisition, general reasoning/presentation, history follow-up, DSA and progressive feedback to false. Runtime itself is optional in configuration, but required for supplied-thread continuation. False defaults are not evidence that deployed paths are unused. Settings validators require runtime + governance + DSA for evidence acquisition; general reasoning also requires claim capture; progressive feedback requires runtime + governance + restraint + privacy. Main forwards most settings explicitly; general reasoning options are resolved by `orchestrate_chat` when omitted. Manual override defaults true but is subordinate to local-only policy.

[Dependencies][C-deps] already include FastAPI 0.115.6, Pydantic 2.10.5, HTTPX >=0.27.0 and PyYAML 6.0.2. CO calls an external OpenAI-compatible LiteLLM endpoint; the Python LiteLLM package is not in this requirements file. No installed gateway version or supported fallback configuration was established. Legacy BMS chat is actually registered; extra CO action/voice/strict paths are source-wired or gated, not proven dead merely because the narrowed MVP defers their breadth.

## Native alternatives: verified capability versus replacement hypothesis

Checked on 2026-11-15 against primary documentation and pinned implementation:

- [LiteLLM fallback documentation](https://docs.litellm.ai/docs/proxy/reliability) documents model-group failover after configured retries. [Router documentation](https://docs.litellm.ai/docs/routing) documents retries, timeouts, cooldowns and load balancing. This verifies a relevant existing product capability, not the installed gateway or CCP privacy/budget/trace equivalence. Limit the candidate to provider reliability mechanics; retain CO's authority checks.
- [Pydantic 2.10 JSON Schema documentation](https://docs.pydantic.dev/2.10/concepts/json_schema/) documents `BaseModel.model_json_schema` and `TypeAdapter.json_schema`. CO pins 2.10.5. This supports replacing duplicated structural declarations in principle, not replacing semantic evidence checks or proving a provider accepts the generated schema. No new library is required.
- The existing CO pipeline is the source-verified replacement owner for BMS direct chat. Migration compatibility and absence of external legacy callers remain unverified. The historical [cross-repository debt record][P-debt] supports this investigation, but is not proof that retirement is already safe.
- The [competitive assessment][P-competitive] discusses established memory/harness/assistant alternatives. It explicitly lacks a matched whole-system comparison. No new validation here proves an agent framework can replace BMS durable association, CR admission and CO disclosure together. Do not add a framework, external policy engine or general scheduler merely to reduce one file's size.
